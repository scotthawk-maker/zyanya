# AstroBWTv3 Proof-of-Work Specification & Hardware Tuning

> **Protocol Version**: AstroBWTv3 / KHeavyHash Hybrid  
> **Consensus Engine**: GhostDAG Parallel Block-DAG (1 BPS Target)  
> **Primary Hardware Class**: Commodity 64-bit Symmetric Multiprocessing (SMP) CPUs  
> **Primary Invariant**: Latency-Bound Memory Hardness with Zero ASIC/FPGA Advantage

---

## 1. Algorithmic Architecture

Zyanya implements a two-stage hybrid Proof-of-Work pipeline combining **AstroBWTv3** (a data-dependent, branch-heavy Burrows-Wheeler Transform algorithm) with **KHeavyHash** (a 64×64 pseudo-random matrix linear transformation). The algorithm is purpose-built to enforce strict memory-latency bottlenecks, rendering compute-dense custom silicon (ASICs) and reconfigurable logic arrays (FPGAs) economically unviable.

```
+-----------------------------------------------------------------------------+
|                          Block Header Context                               |
| (Version, Parent Hashes, Merkle Root, DAA Score, Timestamp, Bits, Nonce)    |
+-----------------------------------------------------------------------------+
                                       |
                                       v
                     [ Stage 1: PowHash Serialization ]
           PRE_POW_HASH || Timestamp (u64) || 32 Zero Padding || Nonce (u64)
                                       |
                                       v
                       [ Stage 2: SHA3 / Keccak Sponge ]
                 200-Byte State Initialization & Permutation
                                       |
                                       v
                    [ Stage 3: AstroBWTv3 Transformation ]
          • Multi-Pass Data-Dependent Buffer Allocation (128 KB - 2 MB)
          • Linear Suffix Sorting (DivSufSort / Induced Sorting)
          • Variable-Length Run-Length & Suffix Array Transformations
          • Data-Dependent Branching & Permutation Loops
                                       |
                                       v
                  [ Stage 4: Matrix Generation (XoShiRo256++) ]
              Deterministic 64x64 Matrix Initialization (Rank = 64)
                                       |
                                       v
                       [ Stage 5: KHeavyHash Execution ]
        • 64-Nibble Vector Expansion
        • 64x64 Matrix-Vector Arithmetic Multiplication
        • 4-Bit Nibble Compression + XOR Mixing + Final Keccak-256
                                       |
                                       v
                   [ Stage 6: Consensus Target Comparison ]
                     Uint256(Hash) <= Uint256(TargetBits)
```

## 2. Mathematical Foundations of AstroBWTv3

AstroBWTv3 operates over variable-length permutation buffers derived from the initial Keccak sponge digest. The mathematical structure relies on three distinct operations:

### 2.1 Sponge State Expansion & Pseudo-Random Generation
Given a 32-byte pre-PoW header hash $H_{\text{pre}}$, timestamp $T$, and nonce $N$:

$$S_0 = \text{Keccak-f}[1600]\left( H_{\text{pre}} \parallel T \parallel 0^{32} \parallel N \right)$$

The initial sponge state $S_0 \in \{0,1\}^{1600}$ is iteratively absorbed and squeezed to generate dynamic length parameters $L_i$ and pre-transform arrays $A_i$:

$$L_i = L_{\min} + \left( \sum_{k=0}^{3} S_0[k] \cdot 256^k \right) \pmod{(L_{\max} - L_{\min} + 1)}$$

Where $L_{\min} = 131,072 \text{ bytes (128 KB)}$ and $L_{\max} = 2,097,152 \text{ bytes (2 MB)}$.

### 2.2 Suffix Array Construction & The Burrows-Wheeler Transform
Let string $X = x_0 x_1 \dots x_{L-1}$ be the generated byte sequence terminated by a unique sentinel symbol $\$ < x_j$. The Suffix Array $\text{SA}(X)$ is a permutation of the integers $\{0, 1, \dots, L-1\}$ corresponding to the lexicographic order of all suffixes:

$$\text{Suffix}(i) = x_i x_{i+1} \dots x_{L-1}$$

$$\text{SA}(X) = [p_0, p_1, \dots, p_{L-1}] \quad \text{such that} \quad \text{Suffix}(p_0) < \text{Suffix}(p_1) < \dots < \text{Suffix}(p_{L-1})$$

The Burrows-Wheeler Transform $\text{BWT}(X)$ constructs a string $L$ of identical length:

$$L[i] = \begin{cases} X[\text{SA}[i] - 1] & \text{if } \text{SA}[i] > 0 \\ \$ & \text{if } \text{SA}[i] = 0 \end{cases}$$

```
+-----------------------------------------------------------------------+
| Suffix Sorting Complexity:                                            |
| Linear time O(L) via Induced Suffix Sorting (SA-IS / DivSufSort)       |
| Peak Working Memory: O(5L) bytes (Original Array + Suffix Table)       |
| Memory Access Pattern: Irregular, random-pointer dereferencing        |
+-----------------------------------------------------------------------+
```

### 2.3 Branch-Heavy Dynamic Permutations
Following the BWT sort, the transformed buffer passes through $k$ rounds of data-dependent mixing. The branch decision at index $j$ is calculated directly from the sorted bytes:

$$\text{BranchCond}(j) = \left( L[j] \oplus S_0[j \bmod 200] \right) \land 0x03$$

Depending on $\text{BranchCond}(j)$, the execution engine branches into divergent mathematical primitives:
- **Case 0**: Modular arithmetic shift & non-linear byte substitution.
- **Case 1**: S-Box non-linear permutation based on AES Galois Field $\text{GF}(2^8)$ multiplication.
- **Case 2**: RC4-like dynamic state swap across active cache lines.
- **Case 3**: Bitwise rotation combined with 64-bit integer carry-less multiplication.

Because the branch target is determined by dynamic BWT output, static speculative execution units cannot predict branch paths, forcing pipeline stalls if memory latency is high.

### 2.4 KHeavyHash Matrix Multiplication
The 32-byte intermediate hash produced by AstroBWTv3 ($H_{\text{bwt}}$) is passed into the KHeavyHash matrix operator:

1. **Matrix Generation**: Using $H_{\text{pre}}$, seed a `XoShiRo256++` PRNG to generate a $64 \times 64$ matrix $M \in \mathbb{F}_{16}^{64 \times 64}$ (4-bit nibbles). Verify that $\text{rank}(M) = 64$.
2. **Vector Expansion**: Expand $H_{\text{bwt}}$ into a 64-element 4-bit nibble vector $\vec{v} \in \mathbb{F}_{16}^{64}$:
   $$v_{2i} = H_{\text{bwt}}[i] \gg 4, \quad v_{2i+1} = H_{\text{bwt}}[i] \land 0\text{x0F} \quad (0 \le i < 32)$$
3. **Linear Transform**: Compute matrix-vector product $\vec{u} = M \vec{v}$ over $\mathbb{Z}$:
   $$u_k = \sum_{j=0}^{63} M_{k,j} \cdot v_j \quad (0 \le k < 64)$$
4. **Compression & XOR Mixing**: Extract high-order bits, pack back to 32 bytes, XOR with the original input hash, and finalize via Keccak-256.

## 3. ASIC and FPGA Immunity Analysis

AstroBWTv3 achieves permanent ASIC/FPGA resistance through fundamental microarchitectural constraints rather than artificial memory-size bloat:

```
+--------------------------------------------------------------------------+
|                        ASIC vs CPU Cost Dynamics                         |
+--------------------------------------------------------------------------+
| Metric                 | SHA-256 ASIC Core       | AstroBWTv3 Core       |
+------------------------+-------------------------+-----------------------+
| Silicon Footprint      | < 0.05 mm² (Pure Logic) | > 4.5 mm² (SRAM+ALU)  |
| Memory Requirement     | Register-only (0 KB)    | 2 MB L3 Cache/Thread  |
| Latency Sensitivity    | Negligible              | Critical (Sub-10ns)   |
| Branch Divergence      | Zero                    | Extreme (Data-Driven) |
| Compute:Memory Ratio   | 10,000 : 1              | 1 : 12                |
+--------------------------------------------------------------------------+
```

### 3.1 The SRAM Area Penalty
An ASIC manufacturer can pack tens of thousands of SHA-256 or Blake3 hash cores onto a single $300\text{ mm}^2$ die because these algorithms require only basic combinational logic and registers.

In contrast, AstroBWTv3 requires a working dataset of up to **2 MB per thread** with **sub-10 nanosecond random access latency**. Embedding 2 MB of high-speed SRAM per core requires:
- $\sim 140 \text{ million transistors}$ per mining core exclusively for memory cells.
- A 64-core ASIC die would require $128 \text{ MB}$ of high-speed L3-equivalent SRAM, resulting in massive die sizes, extreme thermal density, and prohibitive wafer costs ($>\$15,000$ per wafer on 5nm/3nm nodes).
- The cost per hash for custom silicon approaches or exceeds the cost of commodity mass-produced CPUs (AMD EPYC, Ryzen, Intel Xeon).

### 3.2 Memory Latency vs Compute Throughput
FPGAs and ASICs excel at pipeline parallelism where operations are unrolled into continuous systolic arrays. AstroBWTv3 breaks this model:
- Suffix sorting and dynamic branch evaluation require non-sequential, pointer-chasing memory traversals.
- Increasing clock frequency or adding parallel ALUs yields zero performance scaling when ALUs are stalled waiting for data from cache lines ($t_{\text{LATENCY}}$ bottleneck).
- Commodity CPUs utilize out-of-order execution, advanced hardware prefetchers, and ultra-wide low-latency cache hierarchies (L1/L2/L3) engineered over decades with billions of dollars of R&D.

## 4. CPU Hardware Tuning Guide

Maximizing AstroBWTv3 hashrate requires configuring the host CPU memory subsystem, thread scheduling, and cache affinity.

```
+-----------------------------------------------------------------------+
|                          L3 CACHE GOLDEN RULE                         |
|                                                                       |
|             Max Threads = Floor(Total L3 Cache Size / 2 MB)           |
|                                                                       |
| Example: AMD Ryzen 9 7950X (64 MB L3) -> 64 / 2 = 32 Threads Max      |
| Example: AMD Ryzen 7 7800X3D (96 MB L3) -> 96 / 2 = 48 (Cap at 16 T)   |
| Example: Intel Core i9-14900K (36 MB L3) -> 36 / 2 = 18 Threads       |
+-----------------------------------------------------------------------+
```

### 4.1 Thread Allocation & SMT/HyperThreading
- **Cache Eviction Contention**: If total allocated threads exceed $\text{Total L3 Cache} / 2\text{MB}$, worker threads will evict each other's BWT working sets out of L3 cache into system DRAM (DDR4/DDR5).
- **DRAM Fallback Penalty**: DRAM latency ($50\text{--}80\text{ ns}$) is $6\times\text{--}10\times$ slower than L3 cache ($8\text{--}12\text{ ns}$). Once cache thrashing occurs, aggregate hashrate drops by $60\%\text{--}85\%$.
- **Physical Cores vs SMT**: On CPUs where $\text{L3 Cache} < 2\text{MB} \times \text{Logical Threads}$, allocate only **1 thread per physical core**.

### 4.2 Linux Hugepages Configuration
AstroBWTv3 performs thousands of page address translations during suffix sorting. Enabling 2MB and 1GB Huge Pages minimizes Translation Lookaside Buffer (TLB) misses:

```bash
# Check current hugepages allocation
cat /proc/meminfo | grep -i huge

# Calculate required 2MB hugepages (e.g. 64 pages for 32 threads)
# Allocate via sysctl
sudo sysctl -w vm.nr_hugepages=128

# Make allocation persistent across reboots
echo "vm.nr_hugepages=128" | sudo tee -a /etc/sysctl.conf
sudo sysctl -p
```

For large NUMA dual-socket server nodes (AMD EPYC / Intel Xeon), configure 1GB hugepages at boot:
```ini
# Add to GRUB_CMDLINE_LINUX in /etc/default/grub:
default_hugepagesz=1G hugepagesz=1G hugepages=16
```

### 4.3 NUMA Node Pinning & Memory Interleaving
On multi-socket systems or AMD multi-CCD chiplet processors, threads accessing memory across Infinity Fabric or UPI links suffer severe latency penalties. Pin worker threads directly to local NUMA nodes:

```bash
# Inspect NUMA topology
numactl --hardware

# Launch miner pinned to NUMA Node 0 (Cores 0-15 and Node 0 Memory)
numactl --cpunodebind=0 --membind=0 zyanya-miner --threads 16 --mining-address zyanya:...

# For multi-node configurations, launch separate miner instances per NUMA socket
```

### 4.4 CPU Frequency Governors & Power Profiles
Ensure CPU frequency scaling governors are locked to peak performance states to prevent clock throttling during memory stall phases:

```bash
# Set CPU scaling governor to performance on all logical cores
sudo apt-get install -y cpufrequtils
for CPUFREQ in /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor; do
    echo "performance" | sudo tee $CPUFREQ
done

# Verify active clock speeds
grep "cpu MHz" /proc/cpuinfo
```

### 4.5 Memory Subsystem Tuning (DDR4 / DDR5)
While L3 cache holds the primary working set, fast memory sub-timings accelerate initial buffer population and final matrix hashing:
- **Infinity Fabric Clock (FCLK)**: On AMD Zen 3/4/5 architectures, run FCLK in 1:1 synchronous mode with memory controller clock (UCLK).
- **Primary Timings**: Minimize CAS Latency ($t_{\text{CL}}$) and Row Precharge ($t_{\text{RP}}$).
- **Secondary Timings**: Lower $t_{\text{RFC}}$ (Row Refresh Cycle Time) to accelerate memory bank refreshes.
